## 1. Introduction

Every **backend action** the product needs — operator console, analyst app, background jobs — with a **version tag** so Phase 2 can turn this into API contracts without guessing.

This doc answers GRO-271: what each action does, what triggers it, which object it affects, and whether it exists in the repo today.

| Part | Scope |
|------|--------|
| **I** | Operator / admin console actions |
| **II** | Analyst app actions |
| **III** | Shared pipeline, health, background jobs |
| **IV** | Audit — orphan buttons, orphan APIs, version TBDs |

**Version tags** (resolve edge cases in P1-07):

| Tag | Meaning |
|-----|---------|
| **MVP** | Required for first client delivery / demo |
| **Next version** | Agreed follow-up — not blocking MVP launch |
| **Later** | Valuable — no timeline yet |
| **TBD** | Needs product sign-off in P1-07 |

**Repo status**

| Status | Meaning |
|--------|---------|
| **Implemented** | Route exists and matches target behaviour |
| **Partial** | Route exists but incomplete vs target |
| **Planned** | No route — target product requires it |
| **N/A** | Internal only — no user trigger |
